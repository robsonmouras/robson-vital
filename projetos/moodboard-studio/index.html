O problema

Direção visual, garimpada em abas espalhadas

Quem traduz um briefing de cliente cheio de adjetivos — "quero algo mais premium", "com a cara da marca" — em direção visual concreta é o designer. Geralmente isso acontece garimpando referências em várias abas (Pinterest, Unsplash, Behance), sem um lugar único para organizar o que encontra nem para justificar as escolhas depois.

Resultado: contexto perdido entre ferramentas, dificuldade em defender a direção diante do cliente e retrabalho quando o board vive só na cabeça do designer.

Jornada — do briefing ao feedback do cliente

Dois fluxos no mesmo produto

Mapear a jornada completa da Marina deixou claro que o produto precisava resolver duas coisas ao mesmo tempo: um fluxo de curadoria rápido para quem cria (busca → favoritar → montar board) e uma camada de consumo com zero fricção para quem só aprova (link público, sem login).

Cada risco identificado na jornada virou requisito de produto: loading state e mensagens de erro específicas, favoritos persistentes entre buscas, nome obrigatório no board e link público sem exigir conta de quem recebe.

Benchmark — antes de desenhar

Onde as ferramentas existentes ficam devendo

Cinco ferramentas resolvem parte do mesmo caso de uso — coletar imagens, organizar em board e compartilhar — mas nenhuma resolve o combo completo palavra-chave → Unsplash → board → link de cliente em um fluxo só.

Ferramenta Busca de imagem nativa Board em canvas livre Foco em apresentação ao cliente
Milanote Não (clipper de web) Sim (canvas espacial) Médio
Niice Não claro Sim Alto
SampleBoard Não claro Sim Alto (interiores/produto)
Canva Sim (biblioteca própria) Parcial (templates) Alto
Pinterest Sim (nativo) Não (grid fixo) Baixo
Moodboard Studio Sim (Unsplash nativa) Sim (board dedicado) Alto — link read-only, sem conta

A oportunidade. Busca nativa direto na Unsplash, sem clipper ou upload manual. Favoritar com um clique vendo o board se formar ao lado. Link leve e read-only para o cliente, sem exigir conta — o que concorrentes fazem só em plano pago. Login simples, mantendo a barreira de entrada baixa.

Identidade visual

Paleta, tipografia e voz — decididas primeiro

Identidade visual e tom de voz foram tratados como decisões isoladas e documentadas, antes de qualquer linha de código de interface.

60% — Fundo#F2F2F2
30% — Superfície#FFFFFF · texto #464645
10% — CTA#6A1F74 · só ação e estado ativo

O roxo #6A1F74 — extraído do próprio símbolo da marca-mãe — é cor de CTA exclusiva do produto: transmite criatividade sem competir visualmente com as imagens do board. Todas as combinações validadas em contraste WCAG AAA.

Tipografia: Outfit para display/títulos (Light 300 · Regular 400 · Semibold 600 pontual) e Inter para corpo/UI. A frase-assinatura "Encontre, organize, compartilhe." ganhou depois um tratamento serifado com acento circular à mão (Instrument Serif), virou componente único e passou a abrir tanto o login quanto a home.

Tom de voz — quatro pilares

  • Confiante sem ser chato — afirma, não fica em cima do muro.
  • Explicado sem virar manual — contexto em uma frase, dentro do fluxo.
  • Fluxo sem atrito — sem confirmação redundante quando o feedback visual já é claro.
  • Vocabulário de quem já manja — termos técnicos sem tradução (board, rate limit, link read-only).

Em vez de "Ocorreu um erro inesperado, tente novamente mais tarde", a mensagem nomeia a causa real — "Unsplash bateu o limite de buscas agora. Espera um minuto e tenta de novo."

Processo — prompt-to-production

Construído fase a fase, decisão por decisão

Cada ciclo de geração foi documentado: o prompt exato enviado, o resultado obtido e os pontos onde o código exigiu intervenção manual. Escopo fechado e critério de aceite explícito em cada fase.

Fase 0 · Setup

Scaffold da stack, sem nenhuma tela

Infra pura — dependências, tema, convenções

Só o esqueleto: nome da pasta, dependências, tokens de tema (cores 60/30/10, tipografia), convenção de nomenclatura e estrutura interna. Nenhuma tela.

Aqui veio o primeiro ajuste em tempo real: a documentação oficial do Park UI para Tailwind saiu do ar durante o setup. A troca de Tailwind por Panda CSS foi levada ao usuário, decidida e registrada como decisão de arquitetura — não como acidente. (Os ícones Tabler também deram lugar ao Phosphor mais adiante, registrado na decisão 07.)

Prompt enviado ao Claude Code — trecho
Contexto: estou começando o Moodboard Studio, um gerador de moodboard
(busca de imagens via Unsplash, favoritar, montar board, login e link
público). Este é o primeiro prompt — quero SÓ o setup inicial da stack,
sem nenhuma tela, componente visual ou lógica de negócio. Scaffold puro.

## Stack a instalar
- Next.js (App Router) + TypeScript desde o início (create-next-app,
  ESLint, diretório src/). Gerenciador: npm.
- Estilização: Park UI (sobre Ark UI). Confirme na doc oficial os pacotes
  e a versão exigida antes de instalar. Configure apenas o tema claro.
- Ícones: biblioteca Tabler, outline, stroke-width 1.

- Imagens: só placeholder UNSPLASH_ACCESS_KEY no .env.local.example.

## Tokens de identidade visual (aplicar exatamente assim)
- Títulos: Outfit (300/400, 600 pontual). Corpo: Inter (400/500).
- Cores 60/30/10 como tokens de tema: #F2F2F2 / #FFFFFF (texto #464645)
  / #6A1F74 (só CTA e estado ativo).

## Critério de aceite
- npm run dev sobe sem erro. Fontes e tokens aplicados. Lint limpo.
- .env.local.example com os 3 placeholders. README com a stack e o
  padrão de nomenclatura. Git inicializado com o primeiro commit.
Fase 1 · Protótipo de interface

Busca, curadoria e biblioteca de boards — com dados mockados

Valida o fluxo e a linguagem visual, sem API nem persistência

A home vira a própria tela de busca — sem porta de entrada, sem landing — para reduzir a fricção até o valor central: buscar, favoritar, montar board. A biblioteca de boards salvos foi antecipada para esta fase, fechando o ciclo completo com dados falsos antes de existir qualquer persistência.

Os resultados de busca são blocos de cor em gradiente — mock deliberado, que já deixa testar hierarquia, favoritar e o board se formando na base da tela. A tela de login foi desenhada e implementada em código, mas mantida fora do fluxo navegável: decisão consciente para não competir com o que precisava ser validado.

Prompt — tela de busca + board (reconstrução a partir do diff do commit)
A home (/) vira a tela de busca do Moodboard Studio — sem porta de login
na frente, sem tela de entrada separada. O usuário abre a URL e já cai
no fluxo.

Fluxo:
- Estado inicial: título + campo de busca centralizados, hero limpo,
  ilustração abaixo do campo.
- Busca por palavras-chave (texto livre) — sem chamada real a nenhuma
  API, dados mockados.
- Depois da 1ª busca: busca sobe pro topo, aparece um grid de resultados.
- Cada resultado pode ser favoritado / adicionado a um board.
- O board se forma abaixo do grid (largura cheia, não em coluna lateral),
  reunindo tudo que foi favoritado.
- Favoritos persistem entre buscas diferentes na mesma sessão.
- "Salvar" dá só feedback visual (toast) — sem persistência real ainda.

Tipagem: tudo em TypeScript, sem `any` solto nem no dataset mockado.

Tela de login: aproveitar a maquete (v3) e implementar em código de
verdade (/login, LoginForm) — mas FORA do fluxo. Não linkar de lugar
nenhum. Fica pronta pra quando a auth real entrar (Fase 3).

Fase 2 · Consumo real da Unsplash

De dado mockado para busca real

Todos os estados de borda tratados como parte do produto

Troca do mock pela API real da Unsplash. Busca vazia, falha de rede e rate limit tratados como parte do produto, não como exceção — cada um com copy própria, seguindo o guia de tom de voz.

Decisão técnica: a chamada à Unsplash passa por uma Route Handler no servidor — a chave de acesso nunca vai para o bundle do client. Debounce de 300–500 ms na digitação, obrigatório com API real (não existia no mock, onde o filtro era instantâneo).

Prompt enviado ao Claude Code — trecho
Contexto: o fluxo de busca completo (Fase 1) já roda com mock em
src/lib/mock-images.ts. Agora: trocar esse mock pela busca real na
Unsplash. Login continua fora do fluxo (Fase 3) — não mexer nisso.

## O que trocar
- Criar uma Route Handler (src/app/api/search/route.ts) que recebe o
  termo, chama GET https://api.unsplash.com/search/photos no servidor
  com Authorization: Client-ID , e devolve pro client só o que a
  interface precisa (mapeado, não a resposta bruta).
- SearchWorkspace passa a chamar essa rota via fetch.
- Adicionar debounce na digitação (300–500ms).

## Tipagem
Interfaces pra resposta real (UnsplashPhoto, UnsplashSearchResponse) e
uma função de mapeamento UnsplashPhoto -> SearchImage. Sem `any`.

## Estados (cópia exata do guia de tom de voz)
- Loading: "Buscando imagens."
- Sem resultado: "Nada por aqui para '[termo]'. Tenta um termo mais aberto."
- Falha de rede: "Falha de conexão. Verifica sua internet e tenta de novo."
- Rate limit: "Unsplash bateu o limite de buscas agora. Espera um minuto
  e tenta de novo."
Fase 3 · Autenticação e persistência

Login real, board no banco e link público

Supabase Auth · Postgres com RLS · rota /b/[slug] read-only

Login volta a ser portão obrigatório (Supabase Auth). Os boards passam a gravar de verdade no Postgres com RLS por usuário, e cada board ganha um slug público — uma rota somente-leitura (/b/[slug]) que resolve exatamente a necessidade da Beatriz: abrir, olhar, decidir, sem login.

Prompt enviado ao Claude Code — trecho
Contexto: Fase 2 rodando (busca real, favoritar, board em memória). As
tabelas boards e board_images já existem no Supabase, com RLS por dono e
uma função get_public_board(slug) pra leitura pública.

## Autenticação
- Trocar @supabase/supabase-js isolado por @supabase/ssr (clients de
  browser e servidor).
- LoginForm.tsx: signInWithPassword. Erro -> "Email ou senha não bateram.
  Tenta de novo." Sucesso -> redireciona pra /.
- Botão "Entrar com o Google": visível, desabilitado, "Em breve".
- "Sair" na Navbar + email do usuário como indicativo de sessão.

## Proteção de rota
- Middleware checando sessão: sem sessão, / e /favoritos vão pra /login.

## Persistência
- "Salvar" cria linha em boards + uma linha em board_images por item.
  Slug curto e url-safe (nanoid), checando unicidade.
- Remove mock-boards.ts. BoardsLibrary lista os boards do usuário direto
  do Supabase. Renomear / remover imagem / excluir com escrita real.
- "Copiar link" copia /b/, confirmação "Link copiado."

## Página pública
- Nova rota /b/[slug] — Server Component, sem sessão, via
  get_public_board(slug) (nunca select direto). Slug inexistente:
  "Este board não existe ou não está mais disponível." Read-only, sem
  exigir login — requisito central: a Beatriz não pode precisar de conta.
