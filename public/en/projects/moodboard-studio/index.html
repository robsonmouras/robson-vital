The problem

Visual direction, mined from scattered tabs

The designer is the one who turns a client brief full of adjectives — "something more premium", "with the brand's look and feel" — into concrete visual direction. That usually means digging through references across several tabs (Pinterest, Unsplash, Behance), with no single place to organize what they find or to justify the choices later.

The result: context lost between tools, difficulty defending the direction in front of the client, and rework when the board lives only in the designer's head.

Personas

Three people, one board

Marina Costa, 29

UX/UI designer · primary user

Turns brief keywords into a coherent visual board. Needs speed, and needs to reopen the board weeks later without losing the logic behind the choices.

Rafael Nunes, 34

Account manager

Doesn't use Figma. Needs a simple link to present to the client without depending on Marina in real time.

Beatriz Lemos, 41

End client

Opens the link on her phone, with no sign-up, and decides in seconds whether it "feels like the brand".

Journey — from brief to client feedback

Two flows in the same product

Mapping Marina's full journey made it clear that the product had to solve two things at once: a fast curation flow for the person creating (search → favorite → build a board) and a zero-friction consumption layer for the person who only approves (public link, no login).

Every risk identified in the journey became a product requirement: loading states and specific error messages, favorites that persist across searches, a required board name, and a public link that doesn't require an account from whoever receives it.

Benchmark — before designing

Where existing tools fall short

Five tools solve part of the same use case — collecting images, organizing them on a board and sharing — but none solves the full combo keyword → Unsplash → board → client link in a single flow.

Tool Native image search Free-canvas board Client-presentation focus
Milanote No (web clipper) Yes (spatial canvas) Medium
Niice Unclear Yes High
SampleBoard Unclear Yes High (interiors/product)
Canva Yes (own library) Partial (templates) High
Pinterest Yes (native) No (fixed grid) Low
Moodboard Studio Yes (native Unsplash) Yes (dedicated board) High — read-only link, no account

The opportunity. Native search straight from Unsplash, with no clipper or manual upload. Favoriting with one click while watching the board take shape beside it. A lightweight, read-only link for the client that doesn't require an account — something competitors only offer on paid plans. Simple login, keeping the barrier to entry low.

Visual identity

Palette, typography and voice — decided first

Visual identity and tone of voice were treated as isolated, documented decisions, before a single line of interface code.

60% — Background#F2F2F2
30% — Surface#FFFFFF · text #464645
10% — CTA#6A1F74 · action and active state only

The purple #6A1F74 — taken from the parent brand's own symbol — is the product's exclusive CTA color: it conveys creativity without competing visually with the board's images. All combinations validated for WCAG AAA contrast.

Typography: Outfit for display/headings (Light 300 · Regular 400 · occasional Semibold 600) and Inter for body/UI. The signature line "Encontre, organize, compartilhe." (Find, organize, share.) later got a serif treatment with a hand-drawn circular accent (Instrument Serif), became a single component and now opens both the login and the home.

Tone of voice — four pillars

  • Confident without being annoying — it states, it doesn't sit on the fence.
  • Explained without becoming a manual — context in one sentence, inside the flow.
  • Frictionless flow — no redundant confirmation when the visual feedback is already clear.
  • The vocabulary of people who know the field — technical terms left untranslated (board, rate limit, read-only link).

Instead of "An unexpected error occurred, please try again later", the message names the real cause — "Unsplash just hit its search limit. Wait a minute and try again."

Process — prompt-to-production

Built phase by phase, decision by decision

Every generation cycle was documented: the exact prompt sent, the result obtained and the points where the code needed manual intervention. Closed scope and explicit acceptance criteria in every phase.

The prompts below were written in Portuguese and are translated here for reading.

Phase 0 · Setup

Stack scaffold, no screens at all

Pure infrastructure — dependencies, theme, conventions

Just the skeleton: folder name, dependencies, theme tokens (60/30/10 colors, typography), naming convention and internal structure. No screens.

The first real-time adjustment came here: the official Park UI documentation for Tailwind went offline during setup. Switching Tailwind for Panda CSS was raised with the user, decided and recorded as an architecture decision — not as an accident. (Tabler icons also gave way to Phosphor later, recorded in decision 07.)

Prompt sent to Claude Code — excerpt (translated)
Context: I'm starting Moodboard Studio, a moodboard generator
(image search via Unsplash, favoriting, building a board, login and a
public link). This is the first prompt — I want ONLY the initial stack
setup, with no screens, visual components or business logic. Pure scaffold.

## Stack to install
- Next.js (App Router) + TypeScript from the start (create-next-app,
  ESLint, src/ directory). Package manager: npm.
- Styling: Park UI (on top of Ark UI). Check the official docs for the
  packages and required version before installing. Configure the light
  theme only.
- Icons: Tabler library, outline, stroke-width 1.
- Auth/Database: only the Supabase client and environment variables — no
  login screens, sessions or database calls.
- Images: only an UNSPLASH_ACCESS_KEY placeholder in .env.local.example.

## Visual identity tokens (apply exactly like this)
- Headings: Outfit (300/400, occasional 600). Body: Inter (400/500).
- 60/30/10 colors as theme tokens: #F2F2F2 / #FFFFFF (text #464645)
  / #6A1F74 (CTA and active state only).

## Acceptance criteria
- npm run dev starts without errors. Fonts and tokens applied. Clean lint.
- .env.local.example with the 3 placeholders. README with the stack and
  the naming convention. Git initialized with the first commit.
Phase 1 · Interface prototype

Search, curation and board library — with mocked data

Validates the flow and visual language, with no API or persistence

The home becomes the search screen itself — no front door, no landing page — to reduce friction on the way to the core value: search, favorite, build a board. The saved-boards library was pulled forward to this phase, closing the full cycle with fake data before any persistence existed.

Search results are gradient color blocks — a deliberate mock that already lets us test hierarchy, favoriting and the board forming at the bottom of the screen. The login screen was designed and implemented in code, but kept out of the navigable flow: a conscious decision so it wouldn't compete with what needed validating.

Phase 2 · Real Unsplash consumption

From mocked data to real search

Every edge state handled as part of the product

Swapping the mock for the real Unsplash API. Empty search, network failure and rate limit handled as part of the product, not as exceptions — each with its own copy, following the tone of voice guide.

Technical decision: the Unsplash call goes through a server-side Route Handler — the access key never reaches the client bundle. A 300–500 ms debounce on typing, mandatory with a real API (it didn't exist in the mock, where filtering was instant).

Prompt sent to Claude Code — excerpt (translated)
Context: the full search flow (Phase 1) already runs on a mock in
src/lib/mock-images.ts. Now: replace that mock with real Unsplash
search. Login stays out of the flow (Phase 3) — don't touch that.

## What to replace
- Create a Route Handler (src/app/api/search/route.ts) that receives the
  term, calls GET https://api.unsplash.com/search/photos on the server
  with Authorization: Client-ID , and returns to the client only
  what the interface needs (mapped, not the raw response).
- SearchWorkspace starts calling this route via fetch.
- Add debounce on typing (300–500ms).

## Typing
Interfaces for the real response (UnsplashPhoto, UnsplashSearchResponse)
and a mapping function UnsplashPhoto -> SearchImage. No `any`.

## States (exact copy from the tone of voice guide)
- Loading: "Buscando imagens." (Searching images.)
- No results: "Nada por aqui para '[term]'. Tenta um termo mais aberto."
  (Nothing here for '[term]'. Try a broader term.)
- Network failure: "Falha de conexão. Verifica sua internet e tenta de
  novo." (Connection failed. Check your internet and try again.)
- Rate limit: "Unsplash bateu o limite de buscas agora. Espera um minuto
  e tenta de novo." (Unsplash just hit its search limit. Wait a minute
  and try again.)
Phase 3 · Authentication and persistence

Real login, board in the database and a public link

Supabase Auth · Postgres with RLS · read-only /b/[slug] route

Login becomes a mandatory gate again (Supabase Auth). Boards now write for real to Postgres with per-user RLS, and each board gets a public slug — a read-only route (/b/[slug]) that solves exactly Beatriz's need: open, look, decide, no login.

Prompt sent to Claude Code — excerpt (translated)
Context: Phase 2 running (real search, favoriting, in-memory board). The
boards and board_images tables already exist in Supabase, with owner RLS
and a get_public_board(slug) function for public reads.

## Authentication
- Replace standalone @supabase/supabase-js with @supabase/ssr (browser
  and server clients).
- LoginForm.tsx: signInWithPassword. Error -> "Email ou senha não
  bateram. Tenta de novo." (Email and password didn't match. Try again.)
  Success -> redirect to /.
- "Sign in with Google" button: visible, disabled, "Em breve" (Coming
  soon).
- "Sair" (Sign out) in the Navbar + the user's email as a session
  indicator.

## Route protection
- Middleware checking the session: no session, / and /favoritos go to
  /login.

## Persistence
- "Save" creates a row in boards + one row in board_images per item.
  Short, url-safe slug (nanoid), checking uniqueness.
- Remove mock-boards.ts. BoardsLibrary lists the user's boards straight
  from Supabase. Rename / remove image / delete with real writes.
- "Copy link" copies /b/, confirmation "Link copiado."
  (Link copied.)

## Public page
- New route /b/[slug] — Server Component, no session, via
  get_public_board(slug) (never a direct select). Nonexistent slug:
  "Este board não existe ou não está mais disponível." (This board
  doesn't exist or is no longer available.) Read-only, no login
  required — core requirement: Beatriz must not need an account.

Result

A product that works end to end

Not a static mockup — real authentication, real persistence and a real public sharing link, built in incremental, validated phases, each with a closed scope and explicit acceptance criteria.

The level of documentation — decision by decision, with date, reason and consequence in the code — was treated as part of the deliverable, not as a footnote.
